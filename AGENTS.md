# AGENTS.md

Instructions for AI coding agents working in this repository.

## Database — hard rules

- **Never apply migrations.** Do not run `goose up`, `DbManager.Migrate()`, or any equivalent command against any database (local, dev, staging, or production). Do not run `docker compose up` (or similar) in a way that triggers auto-migration on an app you didn't just start for the purpose.
- **Never run destructive or write SQL directly** against a real database (`psql`, `DELETE`, `TRUNCATE`, `DROP`, `UPDATE`, manual `INSERT`, etc.), and never modify `DATABASE_URL` to point somewhere new without asking first.
- **You may create migrations.** Adding a new file under `db/migrations/` (goose format: `<timestamp>_<name>.sql`, with `-- +goose Up` / `-- +goose Down` sections) is fine and expected when a change requires a schema change. Leave it unapplied for a human to review and run.
- **You may edit queries and regenerate code.** Editing `db/queries/*.sql` and running `sqlc generate` to refresh `internal/db/qg` is fine — this only touches generated Go code, not the database itself.
- The one exception is the disposable Postgres containers spun up by tests via `dockertest` (`internal/tests/db.go`) — those are ephemeral, run migrations, and are torn down automatically. Running `go test ./...` is fine; it does not touch any persistent database.
- If a task seems to require actually applying a migration or touching real data to verify something, stop and ask the user instead of doing it yourself.

## Go conventions in this repo

- Module: `github.com/antonaby/shortsbattle/game-server`, Go 1.24. Run `go build ./...` / `go vet ./...` / `go test ./...` from the repo root before considering Go changes done.
- Format with `gofmt`/`goimports` (standard toolchain formatting — no custom style).
- Logging uses `zerolog` (`github.com/rs/zerolog/log`) with structured fields, not `fmt.Println`/stdlib `log`. Follow the existing pattern (`log.Error().Err(err)...Send()`).
- Domain/service errors use `common.ServiceError` (`internal/common/errors.go`) with an error code — prefer wrapping errors that way over returning bare `errors.New` from service code.
- Layering: HTTP handlers live in `internal/api`, business logic in `internal/services`, persistence in `internal/db` (+ generated `internal/db/qg`). Keep handlers thin — they should validate/parse input and delegate to a service, not contain business logic.
- **Never hand-edit `internal/db/qg`** — it's fully generated by `sqlc` from `db/queries/*.sql` and `sqlc.yaml`. Change the `.sql` file and regenerate instead.
- Tests use `testify` and, for anything needing Postgres, `dockertest` + the helpers in `internal/tests`. Follow the existing test files (`*_test.go` in `internal/services`) for patterns/mocks.

## Tech stack cheat sheet

Backend (Go):
- **Echo** (`labstack/echo`) — HTTP router/middleware for the REST API in `internal/api`. Auth is a custom middleware checking a `Bearer` JWT.
- **Centrifuge** (`centrifugal/centrifuge`) — WebSocket layer (`internal/ws`) used to push real-time game-state updates to the Mini App. This is separate from the REST API's request/response flow.
- **pgx / pgxpool** — Postgres driver, pooled via `internal/db.DbManager`. `DATABASE_URL` configures the connection.
- **sqlc** — generates typed Go query code (`internal/db/qg`) from `db/queries/*.sql` against the schema in `db/migrations`. Run `sqlc generate` after editing queries.
- **goose** — SQL migration tool; migration files live in `db/migrations`. See the DB rules above — agents create migrations, humans apply them.
- **go-redis** (`redis/go-redis`) — Redis client, used for caching (`services.NewCachedPlayerService`) and as the broker for **asynq**.
- **asynq** (`hibiken/asynq`) — Redis-backed task queue powering `internal/watchdog`, which advances games between stages on a timer and reacts to Postgres `LISTEN/NOTIFY` events for immediate state changes.
- **go-telegram/bot** — Telegram Bot API client (`internal/bot`), handles onboarding and links a Telegram user to a player + Mini App session.
- **lestrrat-go/jwx** — JWT/JWK signing and validation for the auth tokens issued to the Mini App.
- **go-playground/validator** — request struct validation in the API layer.
- **zerolog** — structured logging everywhere; configured in `cmd/server/logger.go`.

Frontend (`web-app/`, Vue 3 + TypeScript):
- **Vite** — dev server/build tool. `npm run dev`, `npm run build`, `npm run preview`.
- **Vue 3** (`<script setup>` SFCs) with **vue-router** for pages (`src/pages`) and **Pinia** for state (`src/stores`, one store per domain: game, hub, theme, ui, user, video, ws).
- **axios** — REST calls to the Go backend (`src/api`).
- **centrifuge** (JS client) — connects to the backend's Centrifuge WebSocket endpoint for real-time game updates; kept in `ws.store.ts`.
- **Tailwind CSS v4** (via `@tailwindcss/vite`) — styling.
- This is a **Telegram Mini App**: it's expected to run inside Telegram's WebView and use the Telegram Web App JS bridge for auth/context; don't assume a normal standalone-browser environment when reasoning about session/auth flow.

## General expectations

- Keep changes scoped to what's asked; this is a small team project, not a place to introduce new frameworks/abstractions without discussion.
- When a change touches the DB schema, update the migration, the relevant `db/queries/*.sql`, and regenerate `internal/db/qg` together, but leave applying the migration to a human (see DB rules above).
